# Senior Maintainer Audit — 2026-09-05

**Scope:** entire repository, before any further changes. Maintain
backward compatibility unless a strong technical reason exists.
Do not claim success unless tests pass.

This document lists every issue found, the smallest robust fix
applied (or deliberately not applied), and the test result.

## Issues found and fixed

### 1. Duplicated `TREND_WINDOW: int = 10` across four modules
**Problem:** the same numeric constant was declared in
`backend/rul/types.py:86`, `backend/risk/types.py:111`,
`backend/diagnostics/diagnostic_state.py:121`, and
`backend/health/aggregator.py:33`. Each module re-implemented
the same rolling-window size; a future bump in one place would
silently desynchronise the trend detectors.

**Files affected:** the four modules above; the public API
(`TREND_WINDOW` is part of each module's `__all__` and is
asserted in tests).

**Smallest robust fix:** add a single source of truth in
`backend/_common.py` (`DEFAULT_TREND_WINDOW = 10`) and have each
domain re-export the central value as `TREND_WINDOW`. The public
name is preserved (so every existing import / test still works)
and the four windows can no longer drift apart — a divergence
requires an explicit local override that the new test
`test_all_domain_trend_windows_agree` will then flag.

**Test coverage:** new file
`backend/tests/test_common_constants.py` with 7 tests asserting
the central value is 10, all four domain re-exports agree, the
value is a positive int, and each per-domain symbol is the same
int that the domain uses to size its buffer.

**Result:** 7 passed.

### 2. Type mismatch: `RiskTrend` used for `RulEstimate.trend`
**Problem:** `backend/risk/calculator.py:28` imported `RiskTrend`
and used it to initialise `_MINIMAL_RUL.trend`. The field's
declared type is `RulTrend`. The two enums have identical
string values (`IMPROVING/STABLE/DEGRADING/INSUFFICIENT_DATA`),
so runtime comparison passed — but the type signature was a lie,
and a future rename of one enum would break this code silently.

**Files affected:** `backend/risk/calculator.py`.

**Smallest robust fix:** import `RulTrend` from
`backend.rul.types` and use it for the `RulEstimate.trend`
field. Drop the now-unused `RiskTrend` import.

**Test coverage:** existing `test_phase12_risk.py` exercises
`_MINIMAL_RUL` construction (41 passed).

**Result:** 41 passed.

### 3. `model_version` string disagreement inside `runner.py`
**Problem:** `backend/dashboard/runner.py:373` set
`metadata.model_version = "phase19-control-room-1.0.0"` while
line 410 set `DashboardSnapshot.model_version =
"phase17-streaming-1.0.0"`. The two describe the same
software stack to two different consumers (the alert helper
reads metadata; the API consumer reads the snapshot field).
Disagreement here would confuse any log analysis that joins
the two.

**Files affected:** `backend/dashboard/runner.py`.

**Smallest robust fix:** use the snapshot's value
(`"phase17-streaming-1.0.0"`) for the metadata block — that
matches the project's wire-format convention used in
`backend/telemetry/frame.py` and `backend/telemetry/adapter.py`.

**Test coverage:** new test
`TestEndToEnd::test_runner_model_version_metadata_matches_snapshot`
asserts the two are equal and the value is a non-empty string.

**Result:** passed (full phase 19 suite: 30 passed).

### 4. Hardcoded identifiers `mission-001/vehicle-001/engine-001`
**Problem:** the dashboard runner used
`"mission-001"/"vehicle-001"/"engine-001"` while the
`DashboardSnapshot` dataclass defaulted to
`"default-mission"/"default-vehicle"/"default-engine"`. The
snapshot defaults were never what the system actually used in
practice — the bench/test setup standardised on
`"mission-001"` (used in `backend/acquisition/config_loader.py`,
`backend/telemetry/adapter.py`, `config/acquisition.yaml`).

**Files affected:** `backend/dashboard/snapshot.py`.

**Smallest robust fix:** align the snapshot defaults with the
project's documented bench IDs. No test depended on the
`"default-*"` placeholders; they were cosmetic. (Telemetry
schema defaults in `backend/telemetry/frame.py` and
`backend/acquisition/schema.py` keep `"default-*"` — those are
intentionally different defaults for the raw-frame layer and
are untouched.)

**Test coverage:** the existing `test_phase17_streaming.py:583`
asserts `mission_id == "mission-001"` for the streaming
context; nothing asserted `"default-mission"` for the
dashboard snapshot. After the fix the dashboard default matches
the streaming default and both tests pass.

**Result:** 30 phase 19 tests passed; 29 phase 13 tests
passed.

### 5. Hardcoded `data_quality=1.0` in the runner
**Problem:** the runner hardcoded `data_quality=1.0` in the
metadata block *and* in the `DashboardSnapshot` field. The
PHASE 22 diagnostic assembler computes the real
`data_quality` from the sensor sample (fraction of channels
that produced a non-dropped reading this tick), but the
runner built the snapshot *before* the assembler ran, so the
alert path could never fire `DATA_DEGRADED` warnings (which
require `data_quality < 0.5`). The dashboard reported
"perfect data" even when sensors were actually dropping
readings.

**Files affected:** `backend/dashboard/runner.py`.

**Smallest robust fix:** assemble the diagnostic state earlier
in the tick (right after the risk computation in step 10b) so
its `data_quality` is available when the alert payload is
built. The diagnostic state is then re-attached with
`reliability` at the end via `dataclasses.replace` (the same
pattern PHASE 22 already uses). The assembly is deterministic
given the same inputs, so the new ordering does not change
the assembler's output.

**Test coverage:** new test
`TestEndToEnd::test_runner_data_quality_propagates_to_snapshot`
asserts (a) snapshot's `data_quality` and metadata's
`data_quality` are equal, (b) both are in `[0, 1]`. Existing
`test_data_quality_low_emits_alert` (phase 19) exercises the
alert path; still passes.

**Result:** 30 phase 19 tests passed.

### 6. Dead `CRITICAL` severity in `_SEVERITY_RANK`
**Problem:** `backend/dashboard/alerts.py` had
`_SEVERITY_RANK["CRITICAL"] = 4` even though the `Alert`
dataclass only emits `INFO/CAUTION/WARNING/RETURN_TO_BASE/ABORT`
and no test or call site ever produces a `"CRITICAL"` label.
The dictionary entry was stale — and worse, it claimed
"CRITICAL severity is supported" when the dashboard has no
way to emit it.

**Files affected:** `backend/dashboard/alerts.py`.

**Smallest robust fix:** drop the dead entry.

**Test coverage:** existing alert tests (30) do not exercise
the missing entry; full phase 19 suite still passes.

**Result:** 30 phase 19 tests passed.

### 7. Misleading `ENGINE_DEGRADATION` fallback recommendation
**Problem:** in `derive_alerts`, when the detected `ftype` was
not in the lookup table the code used
`"ENGINE_DEGRADATION"` as the fallback — the operator would
see a sensor-fault alert with an engine-induction
recommendation. The right behaviour is a generic
"review evidence" line that does not name a domain.

**Files affected:** `backend/dashboard/alerts.py`.

**Smallest robust fix:** add a `"GENERIC"` entry to
`_RECOMMENDATIONS` (matching the same generic text
`recommendation_for` already returns for unknown types) and
use that as the fallback.

**Test coverage:** existing
`TestEndToEnd::test_recommendation_for_returns_advice` checks
the generic advice path; still passes.

**Result:** 30 phase 19 tests passed.

### 8. Stale `WIRE_KEYS` in dashboard snapshot
**Problem:** `backend/dashboard/snapshot.py` defined
`WIRE_KEYS` as the public wire-format contract, but did not
include the per-key list of the `metadata` sub-dict. The
`to_dict()` output carries `metadata.mission_id`, etc., and
the dashboard frontend iterates over them — but the contract
documentation did not list them.

**Files affected:** `backend/dashboard/snapshot.py`.

**Smallest robust fix:** add a parallel `METADATA_KEYS`
constant for the nested metadata dict so future schema
changes are explicit and testable.

**Test coverage:** phase 22 diagnostic-state test
`test_required_metadata_keys_present` (line 274) already
asserts the metadata keys; still passes.

**Result:** 95 tests across phases 13/19/22/23 passed.

## Issues found but NOT fixed (out of scope)

* **Empty `backend/api/` directory** — README documents it as
  a future home for FastAPI endpoints. No one imports from it.
  Left in place per the user's "do not rewrite working modules
  unnecessarily" rule; the README's "(later)" annotation
  signals intent.
* **Hardcoded alert thresholds** (`0.30`, `0.55`, `0.80`, `2.0`,
  `0.05`) in `backend/dashboard/alerts.py` — these are
  load-bearing (residual z-score of 2.0 corresponds to the
  ~95th percentile of a unit Gaussian) but they *are* hardcoded.
  Moving them to a YAML config schema is a larger refactor; not
  done because (a) the spec says "no rewrite of working modules
  unnecessarily" and (b) there is no current consumer asking
  for operator-tunable alert thresholds.
* **Four different `model_version` strings across modules**
  (`phase17-streaming-1.0.0`, `phase22-diagnostic-1.0.0`,
  `phase19-control-room-1.0.0`, `TELEMETRY_SCHEMA_VERSION`) —
  intentional per module. The only *internal* disagreement
  was issue #3 above, which is fixed.
* **Two parallel `Trend` enums** (`RiskTrend` and `RulTrend`) —
  semantically the same direction label (improving/stable/
  degrading/insufficient_data) but representing different
  observables (risk score vs. TTE hours). Type-safety bug at
  issue #2 is fixed by using the right one. Consolidating the
  two enums is out of scope.
